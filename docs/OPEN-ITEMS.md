# Open items: should we do them?

For every item that is still open after 1.0.0-rc.2: what was measured or found out (not guessed), what it would cost, and a verdict.
Verdicts: **done** - fixed while looking; **do next** - worth it, not yet done; **only if** - worth it when a stated trigger happens;
**no** - not worth it, and why. Dated 2026-11-04; the probes behind the numbers were throwaway CI jobs (not kept).

| 3 | Lock: two processes reaping one abandoned takeover guard both get in | Reproduced on demand (`tests/test_lock_crash.tcl`, "two reapers of one abandoned guard"): both ended up inside, and the second destroyed the first one's new lock (the commit-time check then let only the later one save). | **done** (rc.3): the takeover no longer deletes the lock by name; it looks at the lock without moving it (a hard link), moves only a lock it judged stale - after checking the name still names the file it judged, and comparing again what it moved - and puts a live one back at once; a process re-reads its lock after writing it. | 6 | A real crash-consistency test (block-level, any write cut) | Hosted Ubuntu runners have `dm-flakey` and `dm-log-writes` loaded, loop devices, and mount ext4/xfs/btrfs on a mapped device. | **done** (rc.3): `tests/blockdev_crash.sh` + workflow `blockdev.yml` (no replay tool needed: the log format is parsed in 40 lines of Python). A real file system on a `dm-log-writes` device records every write in completion order; MK Studio makes six commits on it with the durable flushes on (new database, edits, growth, a second editing session with backup); the log is replayed onto a copy of the original image and the power is "cut" after every write (ext4: **318** states, btrfs: **265**, xfs: **96**); each state is mounted (journal recovery) and the database opened as the program opens it: it must hold exactly one of the commits, none older than the last one acknowledged, never reported damaged. **All pass.** The first run found a real defect on ext4 (20 of 222 states): after a power cut an *old* checksum file could sit next to the *new*, good database with the same size and modification second, and the program called it "damaged" (no data lost, but a restore dialog); fixed - the checksum is now removed in the flush that makes the commit record durable and flushed when rewritten (`store::beginCommit`, `sumWrite`; regression checks in `test_durability.tcl`). **Negative control** in the same workflow: with the flushes switched off the test must fail, and does (22 of 33 states: "an acknowledged commit is lost") - so it can tell. Not covered: a write torn inside one sector, a disk that lies, other kernels' file systems (ZFS, NTFS, APFS), Windows and macOS. |

| 19 | Ship the **Metakit fork** (64-bit file positions, `atyr647/metakit`, branch `ccr-7001915e-qdjw33`) in the released programs instead of stock Metakit 2.4.9.7 | **Done in rc.3, in all three runtimes.** The fork is bundled the way mkit-sql is: an exact copy in `tools/vendor/` (first `9ffa269`, now `2e2e482`: the fork's recoverable size errors, two Mk4tcl bug fixes, damaged-datafile hardening, a fuzz of random changes against a model, a Python binding that raises `SizeError`) (`METAKIT-FORK` + the archive, SHA-256 checked by `tools/build-kit.sh`; `tools/sync-metakit-fork.sh` updates it), compiled into the Linux, Windows (mingw) and macOS (arm64 and Intel) kits instead of KitCreator's Metakit (`METAKIT=stock` builds the old way). Checked on each of them in CI with the starpack's own runtime: every suite, `tests/test_wide.tcl` (`EXPECT_WIDE=1`), and `tests/test_widebig.tcl` (2.9 GiB through `store.tcl`, commits across 2 GiB, killed commits). `--info` prints `metakit 2.4.9.7 (files over 2 GiB: yes)`. MK Studio's `store.tcl` learnt the wide format first (a stock Metakit opens a wide file as an empty database, silently) and refuses such a file when it cannot read it. Bringing in `2e2e482` showed that the column guard of the first version counted every value of a text or blob column against the 2^31-1 byte limit, and so refused a blob column at 2 GiB although Metakit moves each value over 10,000 bytes into a column of its own at every commit (a single column took 2.4 GiB with the guard off): the guard now counts what is written since the last commit plus the committed small values, `tests/test_widebig.tcl` puts 2.1 GiB into one blob column, and Metakit's own error is turned into the same refusal (the storage can then only be rolled back: `STORE TAINTED` until Roll Back). One workaround: KitCreator's compile of the fork's `tcl/mk4tcl.cpp` gives `Mk4tcl_Init` C++-mangled, so `build-kit.sh` gives the init functions `extern "C"` linkage - one line that belongs in the fork's `mk4tcl.cpp` (I could not push there). Not used by MK Studio: the Python binding (the fork's own CI tests it). | **done** - what stays yours: the argument against was "a one-person fork of an unmaintained library under every user's data"; the answer is the weekly `metakit-fork.yml` run against the fork's newest commit, and a pinned, checked copy that only moves when `tools/sync-metakit-fork.sh` is run on purpose (to go back: `METAKIT=stock`). |
